# 조직 시뮬레이션 에이전트 — 구성

## 설계 원칙 하나

**LLM이 해야 할 일과, LLM에게 시키면 안 되는 일을 구조로 분리한다.**

한 덩어리 프롬프트로 만들면 반드시 이렇게 된다.
- 인원수를 지어낸다 ("약 30명 정도입니다")
- 없는 조직 이름을 만든다 ("인사기획팀을 통합하면" — 이 회사에는 HR기획팀만 있다)
- 단정한다 ("통합을 권고합니다")

조직 개편은 사람의 생계가 걸린 주제다. 프롬프트로 "지어내지 마세요"라고 부탁하는 대신,
지어낼 수 없는 구조로 만든다.

| LLM이 잘하는 것 | LLM에게 시키면 안 되는 것 |
|---|---|
| 자연어 의도 파악 | 숫자 계산 |
| 되묻기 | 조직 코드 생성 |
| 숫자에 의미 부여 | 중복 여부 판정 |
| 무엇을 먼저 볼지 고르기 | 개인 단위 데이터 취급 |

## 다섯 부분

```
사용자: "대구랑 부산 구축팀 합치면?"
   │
   ▼
┌──────────────────────────────────────────────┐
│ ① 해석기 (LLM)                                │
│    자연어 → 의도 파악, 조직명 후보 추출           │
│    모호하면 되묻는다. 추측하지 않는다.            │
└──────────────────────────────────────────────┘
   │  ["대구구축팀", "부산구축팀"], MERGE
   ▼
┌──────────────────────────────────────────────┐
│ ② 해석·검증기 (결정론적 코드, LLM 아님)           │
│    조직명 → 실제 조직코드 (OrgResolver)          │
│    액션 유효성, 제약 위반, 원장의 기존 판정 조회     │
│    해석 실패 시 ①로 되돌려 되묻게 한다             │
└──────────────────────────────────────────────┘
   │  Plan(MERGE[대구구축팀, 부산구축팀] → 영남구축팀)
   ▼
┌──────────────────────────────────────────────┐
│ ③ 실행기 (순수 계산, LLM 아님)                   │
│    simulate.apply_plan → 구조 델타 · 사람 영향     │
│    연령 구조 · 기능 커버리지 · 지역 간 통합 경고      │
│    같은 입력에 항상 같은 출력                     │
└──────────────────────────────────────────────┘
   │  ToolResult(값, 근거, 가정, 주의, local_only)
   ▼
┌──────────────────────────────────────────────┐
│ ④ 해설기 (LLM)                                │
│    숫자 → 의미. 계산 / 가정 / 판단 필요로 3분할     │
│    14개 지표를 다 읊지 않고 중요한 것만 고른다       │
│    단정 금지 규칙을 여기서 강제                   │
└──────────────────────────────────────────────┘
   │
   ▼
┌──────────────────────────────────────────────┐
│ ⑤ 기록기 (LLM 제안 + 사람 확인)                  │
│    "그건 국사 때문에 안 돼" → 판정 후보로 제시       │
│    사용자가 확인하면 원장에 기록                   │
└──────────────────────────────────────────────┘
```

②와 ③에 LLM이 없다는 것이 이 구성의 핵심이다.
조직코드와 숫자는 모델을 거치지 않는다.

## ① 해석기 — 되묻는 것이 기본값

가장 중요한 규칙: **조직명을 생성하지 않는다.** 사용자의 말에서 후보 문자열을 뽑아
②에 넘길 뿐이다. 실제 조직인지는 ②가 판정한다.

**되물어야 하는 경우** (추측 금지)

| 상황 | 예 |
|---|---|
| 조직명이 모호 | "구축팀" → 6개 중 어느 것인가 |
| 통합 후 팀장 미지정 | 두 팀장 중 누가 남는가 |
| 분할 시 인원 배분 규칙 없음 | 비율인가, 명시 배정인가 |
| 개편 의도 불명확 | 효율화인가, 기능 집중인가, 정년 대응인가 |

마지막 항목은 해설의 초점을 바꾸므로 특히 중요하다. 같은 통합이라도 의도가
"효율화"면 직책자 감소를, "정년 대응"이면 연령 구조를 먼저 말해야 한다.

## ② 해석·검증기 — 지어낼 수 없게 만드는 자리

`agent/resolver.py` 에 구현되어 있다. 현재 스냅샷의 실제 조직 목록에 대해서만
이름을 해석하며, 확실할 때만 코드를 돌려준다.

```
"대구구축팀"   → ok        = 대구구축팀
"DC Eng팀"    → ok        = DCEng팀        (공백·기호 정규화)
"구축팀"       → ambiguous → 6개 목록과 함께 되묻기
"인사기획팀"    → not_found → "혹시 이 중 하나인가요? 영업기획팀, 방송사업기획팀 …"
```

`인사기획팀`은 이 회사에 없다(HR기획팀이 있다). 모델이라면 그럴듯하게 넘어갔을 것이다.

검증 단계에서 함께 확인하는 것
- 액션 유효성 (존재하는 조직인가, 충돌하는 액션인가)
- 제약 조건 (법정 필수 조직, 팀 최소 인원)
- **판정 원장 조회** — 이미 "유지"로 판정된 건이면 시뮬레이션 전에 먼저 알린다

---

## ③ 실행기 — 결정론

이미 구축된 도구 계층이 그대로 실행기다. LLM은 관여하지 않는다.
같은 입력에 같은 출력이 나오지 않으면 신뢰가 생기지 않는다.

| 모듈 | 답하는 것 |
|---|---|
| `structure` | 계층, span, 조직 규모 |
| `dynamics` | 조직 승계, 인원 이동, 이탈 |
| `workforce` | 연령, 승계, 정년, 자연감소 |
| `functions` | 기능 태깅, 병렬 조직군, 중복 후보 |
| `geography` | 근무 지역, 권역 구조 |
| `naming` | 조직명 정합성 |
| `simulate` | 개편 영향 |
| `ledger` | 판정 기록·조회 |

## ④ 해설기 — 계산 / 가정 / 판단의 분리

모든 답변을 세 조각으로 나눈다.

> 영남구축팀 27명이 됩니다. 팀장 1자리가 줄어듭니다. **(계산)**
> 이 계산은 근무지가 기존 그대로 유지된다고 전제합니다. 지역은 조직명에서 추론했습니다. **(가정)**
> 팀장 1명이 대구·부산에 나뉜 27명을 관리하는 것이 실무적으로 가능한지는 판단이 필요합니다. **(판단)**

**금지 표현**: "~해야 합니다", "권고합니다", "최적입니다", "비효율적입니다"
**대체**: "~하면 ○○이 달라지고 ○○ 비용이 발생합니다"

**무엇을 먼저 말할지**는 개편 의도에 따라 다르다.

| 의도 | 먼저 말할 것 |
|---|---|
| 효율화 | 직책자 수, 평균 팀 규모, span |
| 기능 집중 | 기능 커버리지, 잔존 중복, 기능 결손 |
| 정년 대응 | 통합 조직의 연령 구조, 5년 내 정년율 |
| 지역 재편 | 지역 간 통합 경고, 권역별 커버리지 |

## ⑤ 기록기 — 대화에서 판정을 건져 올린다

세션 중 사용자가 판단을 말하면 기록기가 포착해 **판정 후보**로 제시한다.
사용자가 확인해야 원장에 들어간다. 모델이 임의로 기록하지 않는다.

> 사용자: "지역은 그대로 둬야 해. 국사가 거기 있으니까."
> 에이전트: 이렇게 기록할까요?
>   **대상** 구축팀 군 / **판정** 유지 / **사유** 국사가 각 지역에 있어 인력 집중 불가
> 사용자: 응
> → `ledger.record(...)` → 다음 진단부터 이 건은 미판정 목록에서 빠진다

## 상태 모델

에이전트가 들고 있어야 할 것.

| 상태 | 성격 | 비고 |
|---|---|---|
| 기준 스냅샷 | 불변 | 2026-01 현행 조직 |
| 작업 중 시나리오 | 가변 | **누적 편집 가능해야 한다** |
| 시나리오 스택 | 가변 | A안/B안/C안 비교용 |
| 세션 판정 | 임시 | 아직 확인받지 않은 판정 후보 |
| 판정 원장 | 영속 | 확정된 판정 |

**누적 편집이 중요하다.** "거기에 안전보건팀도 합쳐봐"라고 했을 때 기존 시나리오에
액션을 덧붙일 수 있어야 한다. 매번 처음부터 다시 말하게 하면 세션에서 못 쓴다.

## 데이터 경계

`agent/contracts.py` 에 구현되어 있다. 프롬프트로 부탁하지 않고 반환 직전에 검사한다.

```
개인 단위 컬럼(사번·나이·성별·입사일·직책) 포함 → PrivacyError
사번 형태의 값이 컬럼명을 위장해 섞임         → PrivacyError
조직 단위 집계                              → 통과
개인 명단이 필요한 결과                      → local_only 로 분리, 모델은 건수만
```

**컬럼을 조용히 지우지 않고 거부한다.** 사번과 나이만 지운 행은 여전히 한 사람의
기록이고, 익명처럼 보이기 때문에 더 위험하다.

배포 환경(외부 LLM 전송 가능 여부)이 확정되지 않았지만, 경계를 코드로 그어 두면
어느 쪽으로 결론이 나도 ②③⑤와 리포트는 유지되고 ①④만 교체하면 된다.

## 도구 반환 계약

숫자만 반환하는 도구는 만들지 않는다.

```python
ToolResult(
    value       = 집계 결과 (팀 단위 이상),
    basis       = ["2026-01 명단 집계", "R&R 원문: '사업장 안전보건 관리…'"],
    assumptions = ["조직장 직할 슬롯은 팀에서 제외", "지역은 조직명에서 추론"],
    caveats     = ["기능 분류 사전이 시드 상태라 과다 집계됨"],
    local_only  = 개인 명단 DataFrame | None,
)
```

탐색 과정에서 분석 가정이 네 번 틀렸다. 그때마다 사람이 알려줘서 고쳤다.
**가정이 보이지 않으면 교정할 기회도 없다.** 그래서 선택이 아니라 계약으로 둔다.

## 실패 모드와 방어

실제로 겪은 것들이다.

| 실패 | 방어 |
|---|---|
| 없는 조직 이름 생성 | ②가 실제 목록에서만 해석, 없으면 되묻기 |
| 숫자 지어내기 | LLM은 계산하지 않음. 도구 반환값만 인용 |
| 가정 누락 | `ToolResult.assumptions` 를 계약으로 강제 |
| 단정 | ④의 금지 표현 목록 |
| 이미 내린 판정 무시 | ②가 시뮬레이션 전 원장 조회 |
| 지역 제약 망각 | ③이 `cross_region_merges` 를 항상 반환 |
| 개인정보 유출 | `privacy_gate` 가 반환 직전 차단 |

## 구현

**루프**: Anthropic SDK의 tool runner(`client.beta.messages.tool_runner`)로 ①④를 돌린다.
도구 함수는 ②③을 감싼 얇은 래퍼다. 루프를 직접 쓸 이유가 없다.

**모델**: `claude-opus-5`. 적응형 사고(`thinking: {"type": "adaptive"}`)를 켜고
`output_config.effort` 는 `high`. 해석·해설 모두 실수 비용이 높아 낮출 이유가 없다.

**프롬프트 캐싱**: 도구 정의 → 시스템 프롬프트 → 기준 스냅샷 요약(조직 목록·전사 지표)
순으로 앞쪽에 고정하고, 사용자 질문과 시뮬레이션 결과는 그 뒤에 둔다.
조직 목록만 200개가 넘어 세션 내내 재전송되므로 캐시 효과가 크다.
시스템 프롬프트에 날짜·세션 ID 같은 가변값을 넣으면 캐시가 통째로 깨진다.

**세션 중 모드 전환**(예: "이제 보고서 작성 모드로")은 최상위 `system` 을 고치지 말고
`messages` 에 `{"role": "system", ...}` 을 덧붙인다. 캐시된 앞부분이 유지된다.

**스트리밍**: 시뮬레이션 결과 해설은 길어지므로 스트리밍으로 받는다.

## 만들지 않을 것

- 조직도 편집 UI (기존 인사시스템의 몫)
- 모델이 직접 판정을 원장에 쓰는 기능 (사람 확인 필수)
- 개인 단위 배치 추천
- 실시간 인사시스템 연동 (v3 이후)
