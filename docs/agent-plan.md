# 조직 설계 에이전트 — 기획안

## 0. 이 기획의 전제

지난 탐색에서 **분석 가정이 네 번 틀렸다.**

| 틀린 가정 | 실제 | 발견 시점 |
|---|---|---|
| 부서코드가 조직의 정체성이다 | 계층 내 위치 슬롯이라 재사용된다 | 실제 데이터 투입 후 |
| 유사한 R&R = 기능 중복 | 지역 병렬 조직이 후보의 99%를 차지했다 | 첫 실행 결과 13,044쌍 |
| 담당장·본부장도 팀에 속한다 | 자기 이름과 같은 조직에 단독으로 잡힌다 | 팀 수 왜곡 발견 |
| 조직을 합치면 인력이 모인다 | 전국 국사 구조라 사람은 원래 자리에 남는다 | 사용자가 알려줌 |

**이것이 설계의 출발점이다.** 조직 데이터는 회사마다 고유한 규칙을 갖고 있고,
그 규칙은 문서가 아니라 사람의 머릿속에 있다. 따라서 에이전트는
"정답을 내는 기계"가 아니라 **"가정을 드러내고 교정받는 구조"** 여야 한다.

## 1. 무엇을 만드는가

**조직 개편 논의를 위한 대화형 분석·시뮬레이션 도구.**

HR 담당자와 조직 책임자가 **함께 앉아서** 질문하고, 근거를 보고, 개편안을 즉석에서
돌려보고, 판단을 기록하는 도구다. 혼자 돌려서 결론을 받아 보는 배치 리포트가 아니다.

### 하는 일
1. **묻는 대로 답한다** — "구축 기능은 전국 몇 개 팀인가", "5년 내 정년이 가장 몰린 조직은"
   → 숫자 + 근거 원문 + 계산에 쓴 가정
2. **개편안을 즉석에서 돌린다** — "대구랑 부산 구축팀을 합치면?"
   → 구조 델타, 보임 해제 인원, 연령 구조, 지역 간 통합 경고, 제약 위반
3. **판단을 기록한다** — 사람이 내린 판정("이건 의도된 분산")을 저장하고
   다음 분석에 반영하며, 최종 보고서의 근거로 쓴다
4. **자기 가정을 밝힌다** — 모든 답에 "이 계산은 ○○을 전제로 한다"를 붙인다

### 하지 않는 일 — 명시적으로 범위 밖
- 개인별 배치·전환 결정
- 인력 감축 대상 선정
- 평가·보상·승진 관련 판단
- 개편안의 최종 승인 (에이전트는 후보와 영향을 제시하고, 결정은 사람이 한다)

이 경계는 기술적 한계가 아니라 **의도된 설계**다. 조직 개편은 사람의 생계가 걸린
일이고, 근거 없이 기계가 권고하면 실행 단계에서 반드시 무너진다.

## 2. 사용 장면

### 주 사용 장면 — 인터뷰·리뷰 세션 (v1의 초점)
HR 담당자와 조직 책임자가 한 화면을 보며 대화한다.

> **책임자**: 구축팀이 6개인데 많은 건가?
> **에이전트**: 구축 기능은 4개 권역 6개 팀 84명이 수행합니다. 평균 연령 52.6세로
> 전사 평균(46.7)보다 5.9세 높고, 5년 내 정년이 24명(29%)입니다.
> 다만 이 6개 팀은 수남·수북·대구·부산·서부·중부에 각각 위치합니다.
> *조직명에서 추론한 지역이며, 근무지 데이터로 확인이 필요합니다.*
>
> **책임자**: 그럼 대구랑 부산을 합치면?
> **에이전트**: 영남구축팀 27명이 됩니다. 팀장 1자리가 줄고,
> 그 팀장은 대구와 부산에 나뉘어 있는 27명을 관리하게 됩니다(span 기준 12명).
> 평균 연령 52.7세, 5년 내 정년 7명(26%)이라 5년 뒤 20명 규모가 됩니다.
> **이 통합은 인력 집중이 아니라 관리 단위 통합입니다.**
>
> **책임자**: 지역은 그대로 둬야 해. 국사가 거기 있으니까.
> **에이전트**: 기록했습니다. → *판정 원장: "지역 구축팀은 통합 대상 아님 / 사유: 국사 위치 제약"*
> 이후 지역 간 통합안은 이 판정을 먼저 표시하겠습니다.

### 부 사용 장면
- **주기적 진단** — 분기/반기 조직 스냅샷이 갱신되면 진단 리포트 자동 생성
- **보고 자료 준비** — 판정 원장에 쌓인 결정과 근거로 경영진 보고서 초안 작성

## 3. 구조

```
┌─────────────────────────────────────────────────┐
│  대화 계층 — 질문 해석, 도구 선택, 근거와 함께 답변      │
├─────────────────────────────────────────────────┤
│  기억 계층 (신규)                                  │
│   · 판정 원장    사람이 내린 판정과 사유              │
│   · 기능 사전    확정된 전사 기능 분류                │
│   · 제약 조건    건드릴 수 없는 조직, 법정 필수 기능     │
│   · 가정 기록    지역 추론 방식, 승계 기준 등           │
├─────────────────────────────────────────────────┤
│  도구 계층 (구축 완료)                              │
│   loader/quality  적재·무결성                      │
│   structure       계층·span·규모                   │
│   dynamics        조직 승계·인원 이동·이탈             │
│   workforce       연령·승계·정년·자연감소               │
│   functions       기능 태깅·병렬 조직군·중복 후보         │
│   geography       지역 추론·권역 구조                 │
│   naming          조직명 정합성                      │
│   simulate        개편 시뮬레이션·영향 분석             │
├─────────────────────────────────────────────────┤
│  데이터 계층  3개년 명단 · R&R · (추가 예정) 근무지·KPI   │
└─────────────────────────────────────────────────┘
```

도구 계층은 이미 동작한다. **이번에 만드는 것은 대화 계층과 기억 계층이다.**

## 4. 핵심 차별점 — 판정 원장 (Decision Ledger)

대부분의 조직 분석 도구는 "후보 목록"에서 멈춘다. 그 다음이 문제다.
같은 후보를 놓고 매번 같은 논쟁을 반복하고, 작년에 왜 그렇게 결정했는지 아무도 모른다.

판정 원장은 **사람의 판단을 데이터로 만든다.**

| 필드 | 예시 |
|---|---|
| 대상 | 대구구축팀 ↔ 부산구축팀 |
| 기계 판정 | 진성중복 후보 (유사도 0.81) |
| 사람 판정 | **유지 — 통합 대상 아님** |
| 사유 | 국사가 각 지역에 있어 인력 집중 불가 |
| 판정자 / 일자 | ○○○ / 2026-09-20 |
| 유효기간 | 2027 조직개편까지 |

**효과**
- 같은 후보가 다시 올라올 때 이전 판정을 먼저 보여준다
- 중복 후보 58쌍 중 판정이 끝난 것을 제외해 **미판정 건만 남긴다**
- 최종 보고서에서 "왜 이 조직은 손대지 않았는가"에 근거를 제시한다
- 판정 기준이 쌓이면 기계 판정의 초안 품질이 올라간다

## 5. 대화 계층이 쓸 도구 목록

에이전트가 호출할 함수를 이렇게 노출한다. (모두 구현 완료, 래핑만 필요)

| 도구 | 답하는 질문 |
|---|---|
| `org_overview()` | 전사 구조가 어떻게 되어 있나 |
| `find_team(질의)` | 특정 조직의 인원·연령·역할·소속 |
| `function_map(기능?)` | 이 기능은 몇 개 조직이 몇 명으로 하나 |
| `duplicate_candidates(필터)` | 중복 후보는 무엇이고 근거는 |
| `parallel_families()` | 지역·채널로 나뉜 병렬 조직군 |
| `region_view(기능?)` | 이 기능은 전국 몇 개 단위로 운영되나 |
| `org_history(조직)` | 이 조직은 3년간 어떻게 변해왔나 |
| `workforce_risk(조직?)` | 연령·정년·승계 리스크 |
| `naming_check(조직?)` | 이름이 기능을 제대로 드러내나 |
| `simulate(개편안)` | 이렇게 바꾸면 무엇이 달라지나 |
| `compare(시나리오들)` | 여러 안 중 무엇이 나은가 |
| `record_decision(판정)` | 이 판단을 기록해 둬 |
| `recall_decisions(대상?)` | 이 건에 대해 전에 뭐라고 결정했나 |
| `draft_report(범위)` | 보고용 초안을 만들어 줘 |

**설계 규칙**: 모든 도구는 결과와 함께 `근거`(원문 R&R, 계산식)와 `가정`을 반환한다.
숫자만 반환하는 도구는 만들지 않는다.

## 6. 응답 규칙 — 계산과 판단의 분리

에이전트의 모든 답변은 세 부분으로 구성된다.

1. **계산 결과** — 데이터에서 나온 것
2. **가정** — 그 계산이 전제하는 것 (예: 지역은 조직명 추론, 승계 후보군은 연령 기준)
3. **판단이 필요한 지점** — 사람이 정해야 할 것

> 예: "구축팀 6개를 3개로 줄이면 팀장 3자리가 줄어듭니다(계산).
> 단, 이 계산은 근무지가 기존 그대로 유지된다고 전제합니다(가정).
> 한 팀장이 두 지역을 관리하는 것이 실무적으로 가능한지는 판단이 필요합니다(판단)."

**금지**: "이 조직은 통합해야 합니다" 같은 단정. 대신 "통합하면 ○○이 달라지고 ○○ 비용이 발생합니다".

## 7. 범위

### v1 — 함께 보는 분석 도구 (4~6주)
- 대화형 Q&A (도구 14종 래핑)
- 자연어 → 개편안 → 시뮬레이션
- 판정 원장 (기록·조회·분석 반영)
- 진단/시뮬레이션 리포트 생성
- **사용자**: HR 담당자 + 조직 책임자 (함께 사용)

v1을 셀프서비스로 만들지 않는 이유: 가정이 아직 검증 중이고,
잘못된 해석이 혼자 쓰는 환경에서는 교정되지 않는다.

### v2 — 자료 확충 이후
- KPI 연동 → 중복 후보의 실증 (선언 vs 실제)
- 근무지 데이터 → 지역 추론을 실제 값으로 대체
- 인건비 → 개편안의 금액 환산
- 전략과제 → 신설·강화 기능 도출

### v3 — 검증과 확산
- 백테스트: 2025·2026 실제 개편을 입력해 예측과 실제를 비교
- 조직 책임자 셀프서비스
- 정기 모니터링 (분기 스냅샷 자동 진단)

### 하지 않을 것
- 조직도 편집 UI (기존 인사시스템의 몫)
- 개인 단위 배치 추천
- 실시간 인사시스템 연동 (v3 이후 검토)

## 9. 데이터 경계 — 배포 환경이 미정이어도 착수할 수 있게

인사 데이터의 외부 전송 가능 여부가 아직 확인되지 않았다.
**이 불확실성은 설계로 해소한다.** 경계를 아래와 같이 그으면 어느 쪽으로 결론이 나든
도구 계층·판정 원장·리포트는 그대로 살아남고, 교체 대상은 대화 계층 하나뿐이다.

```
개인 단위 데이터 (사번·나이·성별·입사일)
   └─ 로컬 도구 계층에서만 처리. 모델 프롬프트에 절대 포함하지 않는다.

집계 결과 (팀 단위 이상) + R&R 텍스트
   └─ 대화 계층으로 전달 가능

개인 명단이 필요한 출력 (보임 해제 대상 등)
   └─ 로컬에서만 렌더링. 모델은 "N명"까지만 안다.

판정 원장
   └─ 조직 단위 판단과 사유만. 개인 정보 없음.
```

### 설계 규칙
1. 도구 함수는 **항상 집계된 결과**를 반환한다. 개인 행을 반환하는 함수는 대화 계층에 노출하지 않는다.
2. 개인 식별이 필요한 결과는 로컬 파일로 출력하고, 대화 계층에는 건수만 전달한다.
3. 프롬프트에 들어가는 모든 데이터는 전송 전 한 곳에서 검사한다(사번 패턴·나이·성별 컬럼 차단).

### 보안 검토에서 확인할 것
외부 전송 가능 여부만 묻지 말고 아래를 나눠서 물어야 답이 나온다.

1. **개인 식별정보가 제거된 조직 단위 집계값**의 외부 전송이 가능한가?
   (대부분의 규정은 개인정보와 영업비밀을 다르게 다룬다)
2. **R&R 문서의 대외비 등급은 무엇인가?**
   개인정보는 없지만 사업 전략이 담겨 있어 실제 관문은 이쪽일 가능성이 높다.
3. 사내에 **승인된 LLM 서비스** 목록이 있는가?
4. **온프레미스 모델**이 있는가? 있다면 도구 호출을 단순화해 대응한다.

## 10. v1 구현 계획

사용 형태는 **HR 담당자와 조직 책임자가 함께 보는 세션 도구**로 확정.

### Phase 1 — 기반 정리 (1~2주) · 보안 결론과 무관하게 착수 가능
- **기능 분류 사전 확정 세션** (실장님과 1회). 현재 시드 상태라 기능 지도 정확도가 낮다.
  팀별 대표 키워드·전사 빈출 용어 추출 도구는 구현 완료.
- 도구 계층 정리: 함수 시그니처 통일, 반환값에 `근거`·`가정` 필드 부착
- 개인정보 차단 게이트 구현
- 추가 자료 요청 (근무지 > KPI > 인건비 > 전략과제 순)

### Phase 2 — 대화 계층 (2~3주)
- 도구 14종 래핑 및 호출 루프
- 응답 3분할 규칙(계산 / 가정 / 판단 필요) 적용
- 자연어 → 개편안 → 시뮬레이션 경로
- 판정 즉시 기록 흐름 (세션 중 "그건 국사 때문에 안 돼" → 원장 기록)

### Phase 3 — 세션 운영 (1주)
- 한 화면에서 질문·근거·시뮬레이션·판정이 이어지도록 구성
- 세션 종료 시 그날의 판정과 미해결 항목 자동 정리

### 이미 완료된 것
- 도구 계층 9개 모듈 (적재·무결성·구조·동역학·인력·기능·지역·명명·시뮬레이션)
- 판정 원장 (`ledger.py`, `scripts/record_decision.py`) — 기록·조회·분석 반영까지 동작
- 진단/시뮬레이션 리포트 생성

## 11. 미결 사항 — 착수 전 결정 필요

1. **배포 환경** — 9장의 네 가지 질문으로 보안 검토를 진행한다.
   결론이 늦어져도 Phase 1은 착수할 수 있다.
2. **기능 분류 사전 확정 주체와 일정** — 이것 없이는 기능 지도가 의미를 갖지 못한다.
   v1의 최대 병목이다.
3. **판정 원장의 소유자** — 누가 판정을 내리고, 누가 그것을 뒤집을 수 있는가.
   기록에 판정자 이름이 남으므로 사전 합의가 필요하다.
4. **추가 자료 확보 가능성** — 근무지 > KPI > 인건비 > 전략과제 순으로 효용이 크다.
