# 전체 조직 시뮬레이션과 조직도 — 무엇이 빠져 있고 어떤 로직이 필요한가

HR실장의 최종 산출물은 "내년 조직도"다. 지금 에이전트는 **팀 단위 통합·폐지를 쌓아 지표 변화를 보는 것**까지만 한다.
전체 조직을 다시 짜고 조직도로 내놓으려면 아래 여섯 덩어리가 더 필요하다. 순서대로 쌓으면 된다.

## 0. 지금 있는 것과 없는 것

| 있음 | 없음 |
|---|---|
| 팀 단위 MERGE / ABOLISH (웹), MERGE·SPLIT·MOVE·ABOLISH·CREATE·RENAME (파이썬) | 담당·본부 단위 액션 (담당 신설·폐지, 본부 재편, 팀의 담당 이관) |
| 현재 → 개편 후 지표 (팀 수·직책자·관리 폭·연령) | 계층별 지표 (본부당 담당 수, 담당당 팀 수, 계층 깊이, 직급별 직책자 슬롯) |
| 액션을 쌓는 증분 방식 | "목표 조직도"를 그리고 차이를 자동 계산하는 방식 |
| 팀 단위 계보·중복·미션 정합성 | 조직도 그리기·비교·내보내기 |
| 개편안 1개 (편집 중) | 이름 붙인 안 여러 개 저장·비교 (A안 vs B안) |
| 지침·판정·현업 의견 원장 | 개편안 자체의 원장 (누가 언제 어떤 안을 만들었고 어떤 의견이 붙었나) |

## 1. 조직 트리 모델 — 모든 것의 기반

지금 데이터는 팀 목록에 본부·담당 이름이 문자열로 붙어 있다. 조직도를 다루려면 **노드와 부모 링크**로 바꿔야 한다.

```
OrgNode { id, level(본부|담당|팀), name, parent_id, leader_slot(0|1), headcount(팀만), region, functions, rr }
OrgTree { nodes: Map<id, OrgNode>, children(id), ancestors(id), depth(id) }
```

- **id 는 이름이 아니라 코드**. 이름은 바뀌고(개명) 코드는 재사용되므로, 시뮬레이션 안에서만 유효한 임시 id(`sim:…`)를 발급하고 실제 부서코드 부여는 인사시스템 몫으로 남긴다.
- 담당·본부의 인원은 하위 팀 합 + 직할 슬롯(조직장 본인). 지금 `leader_only` 로 표시된 슬롯이 이것이다.
- 근무지(국사·사옥)는 지금 조직명에서 추론한다. 조직도가 목적이면 **근무지 데이터가 필수**다 — 지역 통합의 실제 뜻(사람은 그대로, 관리 단위만 통합)을 조직도에 표시해야 하기 때문.

필요한 데이터 추가: `export_web.py` 가 팀 목록 대신 트리(본부→담당→팀)를 내보내고, 담당·본부 노드에 `leader_slot`, `code` 를 붙인다. 원천은 이미 명단에 있다(담당Ⅰ·담당Ⅱ·팀코드).

## 2. 계층별 액션 — 트리를 바꾸는 최소 연산

팀 단위 액션을 담당·본부로 확장한다. 연산은 여섯 개면 모든 개편을 표현할 수 있다.

| 연산 | 대상 | 뜻 | 사람 영향 계산 |
|---|---|---|---|
| CREATE | 본부·담당·팀 | 새 노드를 부모 아래 만든다 (빈 조직 또는 팀 이관으로 채움) | 조직장 슬롯 +1 (보임 필요) |
| ABOLISH | 본부·담당·팀 | 노드를 없앤다. 하위가 있으면 하위를 먼저 이관·폐지해야 한다 (검증기가 막는다) | 조직장 슬롯 −1 (보임 해제), 팀이면 인원 재배치 |
| MERGE | 같은 계층 2개 이상 | 하나로 합친다. 하위 노드는 살아남는 노드 아래로 옮긴다 | 조직장 슬롯 n−1 해제, 관리 폭·인원 합산 |
| SPLIT | 팀·담당 | 하나를 둘 이상으로 나눈다. 팀 분할은 인원 비율만 지정(개인 배정은 로컬 도구) | 조직장 슬롯 +(n−1) |
| MOVE | 담당·팀 | 부모를 바꾼다 (담당을 다른 본부로, 팀을 다른 담당으로) | 인원 이동 0, 보고 라인만 변경. 상위 조직 인원·관리 폭 재계산 |
| RENAME | 모든 계층 | 이름만 바꾼다 | 없음. 조직명 정합성 검사(naming.py)만 다시 |

규칙:
- 액션은 **순서가 있는 목록**이고, 검증기가 하나씩 적용하며 트리 불변식을 지킨다: 부모는 반드시 존재, 계층은 본부→담당→팀 순서, 순환 없음, 팀은 잎.
- 액션마다 **근거 슬롯**을 둔다: 어떤 지침(id)·판정(id)·현업 의견(id) 때문에 이 액션을 넣었는가. 나중에 "왜 이렇게 짰지"에 답하는 재료.
- 파이썬 `simulate.py` 의 Plan 은 이미 여섯 연산을 갖고 있다. 웹은 MERGE·ABOLISH 뿐이므로 나머지를 옮기고, 대상이 담당·본부일 때의 하위 처리만 추가하면 된다.

## 3. 목표 조직도 방식 — 증분 액션의 반대 방향

실장은 액션을 하나씩 쌓기보다 **"내년 조직도는 이렇다"** 고 그린 뒤 현재와 비교하고 싶어 할 가능성이 크다. 두 방식을 모두 지원하되 내부 표현은 하나(액션 목록)로 둔다.

- **편집기**: 트리를 드래그(팀을 다른 담당으로), 이름 바꾸기, 노드 추가·삭제. 이 편집은 목표 트리(to-be)를 만든다.
- **차이 계산기 (diff)**: as-is 트리와 to-be 트리를 비교해 액션 목록을 **자동 생성**한다.
  - 노드 매칭은 id 우선, id 가 없는 새 노드는 CREATE.
  - 같은 id 인데 부모가 다르면 MOVE, 이름이 다르면 RENAME, to-be 에 없으면 ABOLISH.
  - 여러 as-is 노드가 하나의 to-be 노드를 가리키면 MERGE, 반대면 SPLIT (편집기에서 "합치기/나누기"를 명시적으로 눌러야 id 관계가 남는다).
- 이렇게 얻은 액션 목록을 2번의 검증기·실행기에 그대로 넣는다. 따라서 **지표·제약·사람 영향 계산은 한 벌**이면 된다.

## 4. 계층별 지표와 제약

지금 지표는 팀 기준이다. 조직도 단위로 확장할 것:

| 지표 | 정의 | 왜 필요한가 |
|---|---|---|
| 계층 깊이 | CEO → 본부 → 담당 → 팀 단계 수 (담당이 없는 본부 직할 팀은 2) | "슬림화" 요구가 오면 이 숫자가 목표가 된다 |
| 계층별 관리 폭 | 본부장의 직속 담당 수, 담당장의 직속 팀 수, 팀장의 팀원 수 | 지침 `max_span` 을 계층별로 나눠 적용 (`max_span_hq`, `max_span_dept`, `max_span_team`) |
| 계층별 직책자 슬롯 | 본부장·담당장·팀장 수와 전체 대비 비율 | `leader_ratio_max` 를 계층별로 |
| 1인 담당·1팀 담당 | 하위 팀이 1개인 담당, 하위 담당이 1개인 본부 | 계층만 늘리는 조직의 전형 — 자동 경고 |
| 기능 분산도 | 같은 기능이 몇 개 본부에 퍼져 있나 (function_map 을 트리 위에서 재계산) | 개편 후 중복이 줄었는지 |
| 지역 관리 단위 | 같은 기능이 전국 몇 개 관리 단위로 운영되는가 | 국사 구조를 가진 회사에서 통합의 실제 뜻 |

제약 검사기는 지금처럼 **기준값 옆에 출처(config 또는 지침 id)** 를 붙이고, 발생이 기존인지 신규인지 구분한다. 보호 조직(`protect=`)은 계층에 관계없이 대상이 되면 위반.

## 5. 조직도 그리기·비교·내보내기

- **그리기**: 트리 레이아웃(Reingold–Tilford 정도면 충분, 200 노드)을 SVG 로. 계층은 행, 노드는 상자(이름·인원·조직장 유무). 팀 상자 색은 상태만: 신설(초록 테두리), 폐지(회색·취소선), 이동(파란 테두리 + 원래 부모 표시), 통합(합쳐진 이름 표시). 데이터 색은 쓰지 않는다.
- **비교**: as-is 와 to-be 를 나란히, 또는 하나의 트리에 변화만 강조. 변화 요약 표(액션 목록 + 사람 영향)를 옆에.
- **내보내기**: 팀장의 3개년 보임 조직도 pptx 형식이 이미 있으므로 `python-pptx` 로 같은 서식을 만든다. 웹 아티팩트는 파일 저장이 막혀 있으니 **내보내기는 로컬 파이썬 도구**가 맡고, 웹은 액션 목록(JSON)을 복사하는 버튼까지.
- **개인 배정은 웹에서 하지 않는다**. 사번·이름은 웹에 없다. 통합·폐지로 생기는 보임 해제 **수**와 이동 **수**까지가 웹의 범위이고, 누가 어디로 가는지는 로컬 도구(privacy_gate 안쪽)에서.

## 6. 개편안 원장 — 여러 안을 저장하고 비교

- `scenarios` 컬렉션: `{ name, actions[], basis[], created_by(역할), on, note }`. 지금 "편집 중인 개편안"은 저장되지 않고 새로고침하면 사라진다.
- **비교 뷰**: 두 안의 지표 표를 나란히 (파이썬 `compare_plans` 가 이미 있다). "A안은 팀 −3 / 보임 해제 2, B안은 팀 −1 / 보임 해제 0" 식으로 첫 문장이 나오게.
- 현업 의견은 조직에 붙지만, **어느 안에 대한 의견인지**도 함께 저장(`scenario_id`). 같은 조직이라도 A안에는 반대, B안에는 조건부일 수 있다.
- 실장이 확정한 안은 상태 `확정` 으로 잠그고, 이후 편집은 사본으로.

## 실장에게 먼저 물을 것

1. 개편은 액션을 쌓는 방식과 목표 조직도를 그리는 방식 중 어느 쪽으로 시작하는가 (둘 다 만들되 첫 화면을 정해야 함).
2. 조직도에 반드시 들어가야 하는 정보: 인원, 조직장 유무, 근무지, 기능, 그 밖에.
3. 담당 없는 본부 직할 팀을 허용하는가 (계층 깊이 규칙).
4. 계층별 관리 폭 기준이 그룹 지침으로 있는가 — 있으면 `max_span_hq/dept/team` 으로 등록.
5. 확정된 안의 조직도를 어떤 형식으로 보고하는가 (pptx 서식 그대로인지, 인사시스템 입력용 표인지).
